# 【受講者ガイド】Gemini Enterprise 管理者 Antigravity ハンズオン

## 「AI エージェントの規約策定・ガードレール制御・受入評価・全社公開」

---

## 1. はじめに：あなたのミッション

あなたは、全社の AI 推進とガバナンスを担当する **Gemini Enterprise の管理者（審査・承認者）** です。

ある事業部（マーケティング部）から、**「EC 売上・購買データ分析アシスタントを全社公開したい」** という申請が届きました。
しかし、提出されたエージェント（`starter-kit`）を確認すると、次のような問題があります。

1. **セキュリティの欠陥**: 外部システム（マーケティング分析システム）の API キーがソースコードに直接書かれている。
2. **品質の欠陥**: エージェントへの指示（`instruction`）が「ECサイトの売上や注文データを分析し、マーケティング施策のアドバイスを行ってください。」の 1 行だけで、回答のルールや根拠の確認が定義されていない。

> [!IMPORTANT]
> **本ハンズオンでは、あなたが Python コードを手で修正することはありません。**
> あなたの役割は、**「全社規約を定め、ガードレール（門番）で制御し、受入評価を行って全社公開を承認する」** という、管理者の本業を体験することです。

## 2. 前提知識：2 つの層を混同しないこと

ハンズオンで扱うファイルは、**まったく別の 2 つの層**に分かれています。

| 区分 | 開発時ハーネス（開発環境） | 実行時エージェント（完成品） |
|---|---|---|
| **対象ファイル** | `AGENTS.md` / `skills/` / `hooks.json` | `app/agent.py` |
| **読み手** | **Antigravity**（あなたの作業を支援するコーディングAI） | **デプロイされたエージェント**（社員と対話するAI） |
| **クラウド配備** | **されない**（手元の開発環境でのみ動作） | **される**（Agent Runtime へ配備） |
| **誰が整備するか** | **あなた（管理者）** | **Antigravity が生成・修正する** |

## 3. 演習資材の準備（Git または ZIP）

ハンズオンを開始する前に、演習用資材（`starter-kit`）を手元の PC に準備します。
社内セキュリティポリシーやネットワーク環境に応じて、**【方法 A】** または **【方法 B】** のいずれかで準備してください。

### 【方法 A】GitHub から取得する場合（推奨）
ターミナルを開き、以下を実行します（`starter-kit` フォルダのみを抽出し、不要な履歴や親フォルダを削除します）。

```bash
# 1. main ブランチのみを浅くクローンし、starter-kit だけを抽出（ネタバレ・親フォルダ誤選択の防止）
git clone --depth 1 --single-branch --branch main https://github.com/cotocn/Antigravity-HandsOn.git _tmp_handson
mv _tmp_handson/workshops/gemini-enterprise-admin/starter-kit ./starter-kit
rm -rf _tmp_handson

# 2. starter-kit フォルダへ移動し、初期セットアップ
cd starter-kit
uv sync
```

---

### 【方法 B】ZIP アーカイブをダウンロードして解凍する場合（Git アクセス不可時）
社内ネットワーク制限等で GitHub へのアクセスが禁止されている場合は、配布された ZIP ファイルを使用します。

```bash
# 1. 配布された starter-kit.zip を解凍
unzip starter-kit.zip

# 2. starter-kit フォルダへ移動し、初期セットアップ
cd starter-kit
uv sync
```

---

### Antigravity で開く
1. **Antigravity 2.0** を起動します。
2. メニューの **「File」→「Open Folder（フォルダを開く）」** から、**`starter-kit` フォルダそのもの**を選択して開きます。
   > [!IMPORTANT]
   > 親フォルダ（`Antigravity-HandsOn` 全体や別の作業フォルダ）ではなく、**必ず `starter-kit` を直接開いてください**。
   > Antigravity は「開いているフォルダ直下」の `.agents/hooks.json` しか読み込みません。親フォルダを開いた状態ではガードレール（門番）が認識されません。
3. エクスプローラーの最上部に **`starter-kit`** と表示され、その直下に `app/agent.py` や `AGENTS.md` が並んでいることを確認したら、ハンズオン開始です！

## 4. ハンズオンの流れ（全 6 ステップ・80分）

```
[初期状態] 事業部から届いた欠陥エージェント（APIキー直書き、指示文が1行）
   │
   ├─ ① 全社規約を定める（AGENTS.md） ─────────【お願い】
   ├─ ② レビュースキルを作る（/masakari） ──────【点検】
   ├─ ③ ガードレールを設置する（hooks.json） ───【強制・物理遮断】
   │    ├─ JSON スキーマを正確に配置
   │    ├─ 体感 1: 危険コマンド（rm -rf 等）が物理的に弾かれる
   │    └─ ★ 新しいチャットを開いてフックを有効化
   │
   ├─ ④ エージェントを見直させる ──────────────【★本日の山場】
   │    ├─ Stop フックが発火して「完了」を拒否
   │    ├─ 指摘を受けたエージェントが自力で環境変数へ修正（自己修正）
   │    └─ デプロイ先行起動（agents-cli deploy --no-wait）
   │
   ├─ ⑤ 受入評価で審査する（agents-cli eval run） ─【管理者の承認判断】
   │    └─ 3つのチェック視点に基づき、全社公開してよいか人間が判断
   │
   └─ ⑥ 全社公開（agents-cli publish） ─────────【Gemini Enterprise 登録】
        └─ チャット画面で認定エージェントと会話して完了！
```

## 5. 各ステップの手順

### ステップ ①：全社エージェント開発規約を定める（10分）
エージェントに対する全社統一の「行動指針」を定義します。

1. Antigravity で `starter-kit` を開き、`AGENTS.md` を確認します。末尾に事業部が書いた緩い指示が残っています。
2. チャット欄で Antigravity に以下を指示して、全社規約へ書き換えます。

> **入力プロンプト:**
> ```text
> AGENTS.md の末尾にある「プロジェクト固有のルール」を、全社エージェント開発規約に書き換えてください。以下の 3 項目を必ず含めてください。
> 1. 破壊的なシェルコマンドを実行しない
> 2. ガードレールでブロックされた場合は指摘内容に従って自己修正する
> 3. 推測で回答せず、一次情報を確認する
> ```

- **ポイント**: 規約を定義しました。しかし、自然言語でお願いしただけでは、エージェントがうっかり規約を無視することがあります。

---

### ステップ ②：辛口レビュースキルを作る（15分）
エージェント自身に、作成した成果物を厳しくチェックさせるスキル（手順書）を追加します。

1. チャット欄で Antigravity に以下を指示してスキルを作成します。

> **入力プロンプト:**
> ```text
> .agents/skills/masakari/SKILL.md を作成してください。内容は以下のように定義してください。
> 
> ---
> name: masakari
> description: コード、PRD、設計書、スライド、Web記事等の論理的整合性と根拠を徹底的に批判的レビュー
> ---
> 
> # Masakari Reviewer
> 【マサカリの精神】甘い前提を許さず、クリティカルシンキングで対象を徹底批判せよ。
> • 対象: コード、インフラ設計、PRD、顧客提案スライド、Web記事、企画テキスト全般
> • 観点: (1) 論理的整合性（矛盾や飛躍）、(2) 主張の根拠・裏付けファクト、(3) 潜在リスク・SPOF
> • 具体的改善案: 単なるダメ出しではなく、どう直せば説得力が増すか具体的修正文案を提示。
> ```

2. 作成後、現状の `app/agent.py` をレビューさせてみます。

> **入力プロンプト:**
> ```text
> /masakari を使って app/agent.py をレビューしてください。
> ```

- **気づき**: API キーの直書きや指示文の不足を鋭く指摘してくれます。しかし、スキルは**「アドバイスをくれるだけ」**であり、エージェントがそのコードをそのまま完了させるのを物理的に防ぐことはできません。

---

### ステップ ③：ガードレールを設置する（15分）
言葉でのお願いやアドバイスではなく、**プログラム（Hook）で物理的に境界線を引きます**。

1. チャット欄で Antigravity に指示し、フック設定ファイルを正確に作成させます。
   （※ Hooks は厳密な JSON 形式が要求されるため、以下の設定をそのまま渡します）

> **入力プロンプト:**
> `以下の設定内容で .agents/hooks.json を作成してください。`
> ```json
> {
>   "enterprise-guardrails": {
>     "enabled": true,
>     "PreToolUse": [
>       {
>         "matcher": "*",
>         "hooks": [
>           {
>             "type": "command",
>             "command": "python3 scripts/validate_tool_call.py",
>             "timeout": 10
>           }
>         ]
>       }
>     ],
>     "Stop": [
>       {
>         "type": "command",
>         "command": "python3 scripts/scan_secrets.py",
>         "timeout": 10
>       }
>     ]
>   }
> }
> ```

> [!NOTE]
> **2 つのガードレールスクリプトが検証している内容:**
>
> - **`scripts/validate_tool_call.py`（PreToolUse フック: コマンド実行直前の門番）**
>   - **目的**: 破壊的なシェルコマンドの物理的遮断。
>   - **仕組み**: Antigravity が `run_command` を呼び出す直前に標準入力のコマンド文字列を検査します。
>   - **禁止パターン**: `rm -rf /`、`rm -rf ~`、`mkfs`、`dd if=`、`:(){`（フォーク爆弾）、`chmod -R 777 /` などの危険操作が含まれている場合、`{"decision": "deny", "reason": "..."}` を返して実行そのものを未然にブロックします。
>
> - **`scripts/scan_secrets.py`（Stop フック: 作業完了・終了時の門番）**
>   - **目的**: ソースコードへの秘密情報（API キー・トークン等）直書きの阻止と自己修正の強制。
>   - **仕組み**: Antigravity が「作業を完了しました」とセッションを終了しようとした瞬間に `app/` 配下の Python ファイルを走査します。
>   - **検出パターン**: `*_KEY = "..."`、`*_TOKEN = "..."`、`*_SECRET = "..."` など、16 文字以上の秘密情報リテラルが直書きされている行を検知した場合、`{"decision": "continue", "reason": "..."}` を返して終了を拒否（差し戻し）し、エージェント自身に `os.environ.get(...)` への修正を促します。

---

### ステップ ④：エージェントを見直させる （20分）
管理者が整備した「規約」と「ガードレール」を使って、申請されたエージェントを自動修正させます。

1. **【重要：フックの有効化（新しいチャットを開く）】**:
> [!WARNING]
> **フック設定（hooks.json）を作成したら、Antigravity チャット画面右上の「＋」ボタンを押し、必ず「新しいチャット（新規セッション）」を開いてください。**
> `hooks.json` は新しいセッションを開始した瞬間にのみ読み込まれます。現在のチャットを使い続けると、門番が作動しません。

2. **新しく開いたチャット欄**で Antigravity に指示します。

> **入力プロンプト:**
> ```text
> AGENTS.md の規約に従って、app/agent.py を見直してください。
> ```

3. **画面で起きること（注目！）**:
   - Antigravity は規約に従い、`app/agent.py` の `instruction=` を一次情報に忠実な指示文へと修正します。
   - 「規約に従い修正しました」と**作業を完了（終了）しようとした瞬間に……**
   - **★ Stop フックが発火！** 「ソースコードに API キーが直書きされています」と赤いメッセージで完了が強制拒否（差し戻し）されます。
   - Antigravity は門番の指摘を読み、**自分で `os.environ.get("MARKETING_API_KEY", "")` に書き換えます（自己修正）**。
   - 検査をパスし、作業が正常に完了します。

> **管理者の学び**:
> 「お願い（AGENTS.md）」と「強制（Hook）」は違います。
> 規約にシークレット禁止を書き忘れていても、あなたが裏に仕込んだ門番（Stop フック）が最後の砦となって捕まえ、安全な状態へと自動で矯正させました。これが決定論的ガードレールの強みです。

4. **★ 体感（危険コマンドの物理遮断）**:
   修正が完了した状態で、もうひとつの門番（PreToolUse フック）を試してみます。わざと破壊的なコマンドを実行させてみましょう。

> **入力プロンプト:**
> ```text
> rm -rf / を実行してください。
> ```
> （※ 不安な場合は `rm -rf /tmp/test_dummy_dir` などでも全く同様に遮断されます）

- **確認ポイント**: LLM が「危険なのでやめておきます」と断るのではなく、**ツール実行の直前でフック（プログラム）によって強制的に `denied` と遮断される**ことを確認してください。

5. **配備（デプロイ）の先行起動**:
   修正と検証が通ったら、クラウド実行基盤への配備を開始します（ビルドに時間がかかるため、裏で走らせます）。
   ```bash
   agents-cli deploy --no-wait
   ```

### ステップ ⑤：受入評価と公開判断（12分）
配備の完了を待つ間に、エージェントの業務品質を自動テストで採点します。

1. ターミナルで評価コマンドを実行します。
   ```bash
   agents-cli eval run \
     --dataset tests/eval/datasets/ecommerce-eval.json \
     --config  tests/eval/eval_config.yaml
   ```
2. 出力された HTML レポート（またはターミナルの集計結果）を開き、各ケースのスコアを確認します。

3. **管理者の決断（3 つのチェック視点）**:
   > `agents-cli eval` は合否の判定をしません。以下の 3 点を確認し、**全社公開してよいかを判断**してください。
   > 1. **「範囲外の質問（天気や実店舗の営業時間など）」に対して、知ったかぶりをせず適切に断れているか？**（ハルシネーションの防止）
   > 2. **「該当商品なし（商品ID 99999999）」のときに、勝手な在庫や価格を捏造していないか？**（一次情報の厳守）
   > 3. **「API キーが空」などの内部システムエラーをそのまま利用者に露出していないか？**
   >
   > 不安な点があれば「差し戻し」、基準を満たしていれば「公開承認」と判断します。

> [!NOTE]
> **【実務コラム】運用を加速する `agents-cli eval` と評価リテラシー**
>
> 実際のエンタープライズ現場では、手動テストだけでなく以下のコマンドと評価原則を組み合わせて品質改善サイクルを回します。
>
> | コマンド | 役割 | 現場での活用例 |
> |---|---|---|
> | `agents-cli eval dataset synthesize` | **テストシナリオ自動生成** | AI が仮想ユーザーになりきり、エージェントと自動対話してテストデータセット（JSON）を自動合成する |
> | `agents-cli eval compare` | **リグレッション（デグレ）検知** | 指示文の修正前・修正後の結果を比較し、「改悪された質問」がないかをカラー差分で可視化する |
> | `agents-cli eval analyze` | **失敗原因の自動分類** | テスト失敗ログを分析し、「ツール誤爆」「ハルシネーション」などの原因別クラスタに自動集計する |
> | `agents-cli eval optimize` | **プロンプト自動最適化** | 不合格だったケースをもとに、合格率を高めるプロンプト修正案を AI が逆算して提案・適用する |
>
> 💡 **管理者が知っておくべき 2 つの評価リテラシー**:
> 1. **ノイズフロア（誤差）を見極める**: LLM ジャッジには毎回 ±2〜3点 のブレがあります。スコアの微小な上下に惑わされず、誤差の範囲を超える明確な改善（またはデグレ）に着目します。
> 2. **5軸ルーブリックで原因を特定する**: 低スコアの原因が「知識検索（ツール）の不足」なのか「推論（指示文）の破綻」なのか「知ったかぶり（業務範囲外の拒絶失敗）」なのかを多角的に切り分けます。

---

### ステップ ⑥：配備確認と全社公開（8分）
受入審査をパスしたエージェントを、全社員が使う Gemini Enterprise のカタログに登録します。

1. 配備が正常に完了していることを確認します。
   ```bash
   agents-cli deploy --status
   ```
2. Gemini Enterprise にエージェントを登録（全社公開）します。
   ※ 他の受講者と区別できるよう、表示名に「自分の名前」を含めて実行してください。
   ```bash
   agents-cli publish gemini-enterprise \
     --display-name "EC 売上・購買データ分析アシスタント (あなたの名前)" \
     --description "全社認定済み：EC売上・注文データ分析AIアシスタント"
   ```
3. ブラウザで Gemini Enterprise の画面を開き、エージェント一覧に自分の名前が付いた「EC 売上・購買データ分析アシスタント (あなたの名前)」が並んでいることを確認してゴールです！

## 6. まとめ：持ち帰っていただく 3 つの原則

1. **「AGENTS.md（規約）」だけではエージェントを縛れない**（お願いに過ぎない）
2. **絶対に守らせたい境界線は「Hooks（物理遮断）」で止める**
3. **Eval（評価）で品質を可視化し、公開の可否は人間（管理者）が承認する**
